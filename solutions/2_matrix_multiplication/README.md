# Matrix Multiplication

[LeetGPU 题目](https://leetgpu.com/challenges/matrix-multiplication) · challenge 2 · 官方定义 `2_matrix_multiplication` · 语言 `cute`

## 题目

`A`（`M × N`）、`B`（`N × K`）、`C`（`M × K`）是 GPU 上按行存放的 `float32` 矩阵。计算 `C = A × B`，结果直接写入 `C`。约束为 `1 ≤ M, N, K ≤ 8192`。

- 性能测试：`M = 8192`，`N = 6144`，`K = 4096`，`A`、`B` 的取值在 −10 到 10 之间
- 判定：`atol = 0.0001`，`rtol = 0.0001`

## 评审

### 结论

- **现状：** v5 的 6.56242 ms 是 CuTe 在 H100 上的第 1 名，第 2 名是 57.42793 ms，榜上没有可参照的成绩。
- **版本之间：** 相邻版本都能区分，差距最小的是 v4 → v5 的 31.6%。每个版本只有一次成功提交，波动按 5% 假定。v2、v3 比 v1 慢，v4、v5 比 v1 快。

### 代码

- `v5_tensor_core.py:279` **测试覆盖**：快内核 `_gemm_split` 只在对齐的尺寸上运行。官方 14 个功能用例里只有 8192 × 6144 × 4096 一例走到它，其余 13 例（各维不超过 32）和 `make run` 的示例都走 `_gemm_any`；v4 相同（`v4_aligned.py:251`）。下一版：改动快内核之后，先用对齐的尺寸自测再提交。
- `v5_tensor_core.py:204` **未验证**：一次自测（8192 × 6144 × 4096，取值 −1 到 1，不是提交记录）里，v5 比 `torch.matmul` 更接近 `float64` 的结果，但有 178 / 33,554,432 个输出与 `torch.matmul` 的差超过 `atol + rtol·|ref|`，v4 是 0 个。提交通过了，平台怎样判定没有公开。下一版：改动累加方式时先自测这一项。
- `v5_tensor_core.py:182` **未验证**：拆分要求输入的绝对值小于 65504（FP16 的上限），超出时 `hi` 变成 inf。官方用例的取值都在 −10 到 10 之间，题目约束没有给出值域。下一版：把这个前提写进文档字符串。
- `v5_tensor_core.py:229` **未验证**：后备内核 `_gemm_any` 一个线程算一个输出。大而不对齐的尺寸没有官方用例，慢多少、会不会超时都没测过。下一版：后备内核换成 v1 的内核，它通过了全部官方用例。
- `v5_tensor_core.py:50-53` **未验证**：`PAD` 注释里的 bank 数是按 MMA 片段的排布推算的，没有量过。第 18-21 行"主乘积在 MMA 内累加会损失精度"来自文献和数值模拟，没有在 H100 上比较过。
- `v3_pipelined.py:154-178` **多余**：v3 与 v4 的 tile、流水线和布局相同，只差内核里的边界处理（带谓词的拷贝和写回、移位的首个 k-tile、smem 清零），latency 是 29.01978 对 9.59195 ms；哪一部分贵没有拆开量过。下一版：边界处理留在快内核之外。
- `v2_tiled.py:141-146` **未验证**：v2 比 v1 慢的原因没有拆开：循环里带谓词的拷贝（推测，依据是 v3 → v4），或 A 写入 smem 时一个 warp 只落在 2 个 bank 上（推断，按第 54、192 行的布局算的）。
- **做得好的：** 尺寸判断放在 `solve` 里（`v5_tensor_core.py:279`），快内核里没有边界判断；在平台上试出来的两条 `cute.gemm` 用法记在用到它们的地方（`v5_tensor_core.py:117-120`、`190-194`）。

### 性能机会

单次结果低于 6.23430 ms 才算比 v5 快。空间（推断）：性能测试是 2 × 8192 × 6144 × 4096 次浮点运算，v5 相当于 62.8 TFLOPS，已是 H100 的 FP32 峰值 67 TFLOPS 的 94%。FP16 tensor core 的稠密峰值是 989 TFLOPS，每个 FP32 乘积用三次 MMA，上限约 330 TFLOPS（峰值取自 NVIDIA 数据表），所以 v5 的时间主要花在 MMA 之外。

1. **每个值只拆一次**：每个 k-tile 每个线程拆 48 个值（A 32 个、B 16 个，第 181-188 行），而每个线程分到的数据只有 16 个，同一个值被几个 warp 各拆一次。假设是拆分占了寄存器阶段最大的一块。实验：`cp.async` 落到 smem 之后，每个线程把自己的 16 个值拆成两份 FP16 写回 smem，多一道屏障，MMA 直接读 FP16。
2. **校正项留在 MMA 里累加**（并入下一版，不单独提交）：`corr` 在每个 k-tile 的每一行都清零，再乘一次 1/2048（第 199、204 行）。校正项的和最后要除以 2048，在 MMA 里累加的截断也一起缩小（推断），所以可以整个内核不清零，收尾时乘一次；多用 48 个寄存器。预期收益小于机会 1（推测）。
3. **换成 warpgroup MMA**（在机会 1 之后）：`cute.nvgpu.warpgroup.MmaF16BF16Op` 的 A 操作数可以直接取自 smem（`OperandSource.SMEM`），省掉 A 片段的装载（推测）。它要求 smem 里已经是 FP16，改动也最大。

## 版本

### v1 · Manual（`v1.py`）

一个 CTA 用 256 个线程算 C 的一个 64 × 64 tile，每个线程 16 个输出。沿被求和的维度每次取 16 个元素：线程按手写的下标把 A、B 的切片读进 smem，越界处补 0，然后每一步读 4 + 4 个值，用 `cute.gemm` 做 16 次乘加。网格的 x 轴沿 C 的列。

### v2 · Tiled（`v2_tiled.py`）

算法与 v1 相同，下标换成 layout：`local_tile` 取 tile，tiled copy 做 gmem → smem，tiled MMA 划分每个线程的输出，边界用谓词张量。为了让不完整的 k-tile 只出现在开头，把 A、B 沿 k 向前移了一段，并先把 smem 清零。网格的 x 轴改成沿 C 的行。

### v3 · Pipelined（`v3_pipelined.py`）

照 CuTe 的 `ampere/sgemm.py` 示例：128 × 128 的 tile，每个线程 8 × 8 个输出，三段 `cp.async` 流水线，A 的 smem 步长加 4 以错开 bank。边界仍然用谓词在内核里处理。网格的 x 轴回到沿 C 的列。

### v4 · Aligned（`v4_aligned.py`）

把 v3 的边界处理全部拿掉。`solve` 判断尺寸：各维都是 tile 的整数倍、且至少有 3 个 k-tile 时走流水线内核，否则走一个线程算一个输出的 `_gemm_any`。

### v5 · Tensor core（`v5_tensor_core.py`）

保留 v4 的框架，把 FP32 乘加换成 FP16 的 tensor core MMA（16 × 8 × 16，FP32 累加）。每个输入拆成两个 FP16，`a = hi + lo / 2048`；乘积取 `hi·hi` 和两个校正项，丢掉相对大小 2⁻²² 的 `lo·lo`。主乘积每 16 步从零开始，结果在 MMA 之外用 FP32 累加。
