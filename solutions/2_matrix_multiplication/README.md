# Matrix Multiplication

[LeetGPU 题目](https://leetgpu.com/challenges/matrix-multiplication) · challenge 2 · 官方定义 `2_matrix_multiplication` · 语言 `cute`

## 题目

`A`（`M × N`）、`B`（`N × K`）、`C`（`M × K`）是 GPU 上按行存放的 `float32` 矩阵。计算 `C = A × B`，结果直接写入 `C`。约束为 `1 ≤ M, N, K ≤ 8192`。

- 性能测试：`M = 8192`，`N = 6144`，`K = 4096`，`A`、`B` 的取值在 −10 到 10 之间
- 判定：`atol = 0.0001`，`rtol = 0.0001`

## 评审

标"自测"的数字不是提交记录。它们是在平台的 GPU 上用附在 `make run` 里的脚本量的，尺寸 8192 × 6144 × 4096，没有另外说明时取值在 −1 到 1 之间；脚本不在仓库里。

### 结论

- **H100 现状：** v6 的 3.61978 ms 是 CuTe 的第 1 名，第 2 名是 57.42793 ms，榜上没有可参照的成绩。
- **H100 版本之间：** 相邻版本都能区分，差距最小的是 v4 → v5 的 31.6%；v5 → v6 快 44.8%。每个版本只有一次成功提交，波动按 5% 假定。
- **B200 现状：** v7 的 1.78198 ms 是 CuTe 的第 1 名，第 2 名是 8.1192 ms。B200 上只有这一次提交，没有可比的旧版本；v5 在 B200 上的自测是 5.650 ms。

### 代码

- `v6_warpgroup.py:319` **测试覆盖**：快内核只在 M、K 是 128 的倍数、N 是 32 的倍数（v7 是 64，`v7_tcgen05.py:374`）并且地址按 16 字节对齐时运行。官方 14 个功能用例里只有 8192 × 6144 × 4096 一例走到它，其余 13 例（各维不超过 32）和 `make run` 的示例都走 `_gemm_any`。下一版：改动快内核之后，先用对齐的尺寸自测再提交。
- `v6_warpgroup.py:249` **未验证**：自测里与 `torch.matmul` 的差超过 `atol + rtol·|ref|` 的输出，v6 是 180 / 33,554,432，v7 是 218（`v7_tcgen05.py:291`）；取值 −10 到 10 时是 156,328 和 157,684。两个版本都比 `torch.matmul` 更接近 `float64` 的结果，提交也都通过了，平台怎样判定没有公开。下一版：改动累加方式时先自测这一项。
- `v6_warpgroup.py:78` **未验证**：`lo = a − hi` 不再乘 2048（`v7_tcgen05.py:85` 相同）。输入的绝对值要小于 65504，否则 `hi` 溢出；`lo` 小于 6.1e-5 时是 FP16 的次正规数，误差至多 3e-8。官方用例的取值都在 −10 到 10 之间，题目约束没有给出值域。下一版：见 B200 的机会 2。
- `v6_warpgroup.py:256` **未验证**：后备内核 `_gemm_any` 一个线程算一个输出（`v7_tcgen05.py:311` 相同）。它还要接住 N 不是 32（v7：64）的倍数的大尺寸，例如 N = 6128；没有官方用例，慢多少、会不会超时都没测过。下一版：后备内核换成 v1 的内核，它通过了全部官方用例。
- `v6_warpgroup.py:165` **多余**：`main.fill(0.0)` 没有用，`main` 在每组 k-tile 的第一条 MMA 里被整个覆盖。下一版：删掉。
- `v5_tensor_core.py:90-91` **多余**：smem 的 16 字节对齐在 v5 里没有用处：`cp.async` 一次拷一个值，tensor core 片段的值在 smem 里不相邻，`autovec_copy` 只能逐个读。
- `v3_pipelined.py:154-178` **多余**：v3 与 v4 的 tile、流水线和布局相同，只差内核里的边界处理，latency 是 29.01978 对 9.59195 ms；哪一部分贵没有拆开量过，v2 比 v1 慢的原因（`v2_tiled.py:141-146`）也没有。下一版：边界处理留在快内核之外。
- **做得好的：** 尺寸和对齐的判断都在 `solve` 里，快内核里没有边界判断；在平台上试出来的两件事写在用到它们的文件开头：普通写入的 smem 要先做 proxy fence 才能被 MMA 读到（`v6_warpgroup.py:31-33`，不做时自测有 12% 的输出超出容差），和总和不能一直留在 tensor memory 里（`v7_tcgen05.py:26-28`，自测有 4% 超出容差）。

### 性能机会

**H100：** 单次结果低于 3.43879 ms 才算比 v6 快。空间（推断）：性能测试是 2 × 8192 × 6144 × 4096 次浮点运算，v6 相当于 113.9 TFLOPS。FP16 tensor core 的稠密峰值是 989 TFLOPS（NVIDIA 数据表），每个 FP32 乘积用三次 MMA，上限约 330 TFLOPS，v6 在它的 35%。

1. **加深 k-tile**：v6 每 16 步 k 做一次屏障、一次 proxy fence 和一次等待。依据：在 B200 的自测里，k-tile 从 16 步加到 64 步，时间从 3.31 降到 1.93 ms；H100 上的同一个实验两次都没能启动 GPU，没有数据。实验：`BK` 取 32 或 64，一个 k-tile 里每个乘积发两条或四条指令，仍然每 32 步 k 并入一次 FP32 累加器。
2. **减少重复读入**（推测，在机会 1 之后）：A 的每个元素被 32 个 CTA 各读一次，B 是 64 次，合计 12.9 GB。H100 的 cluster 能让几个 CTA 共用一次读入，但 CuTe 的例子靠 TMA 完成，TMA 只能原样搬 FP32，拆分得改回 smem 里做；改动大。

**B200：** 单次结果低于 1.69288 ms 才算比 v7 快。空间：自测里全程 1.69 ms，去掉 MMA 是 1.26 ms，去掉拆分是 1.06 ms。MMA 本身约 0.4 ms，其余在拆分、读 tensor memory 和每个 k-tile 的同步上。

1. **128 × 256 的 tile**（推测）：一条指令覆盖 256 列，A 的每个元素只被读 16 次。代价是每个 CTA 的 smem 约 196 KB、tensor memory 256 列，一个 SM 上能同时运行的 CTA 变少。先自测。
2. **TF32 的 MMA**（推测）：`tcgen05.MmaTF32Op` 直接读 FP32，拆分不必经过 FP16，也就没有 65504 和次正规数的限制。它一条指令只覆盖 8 步 k，硬件怎样把 FP32 截成 TF32 也要先在自测里确认。
3. **不值得单独提交的两项**（并入下一版）：1024 个线程（自测 1.65 对 1.69 ms）和每 128 步 k 才并入一次累加器（256 线程时 1.89 对 1.93 ms），差距都不到 5%。

## 版本

### v1 · Manual（`v1.py`）

一个 CTA 用 256 个线程算 C 的一个 64 × 64 tile，每个线程 16 个输出。沿被求和的维度每次取 16 个元素：线程按手写的下标把 A、B 的切片读进 smem，越界处补 0，然后每一步读 4 + 4 个值，用 `cute.gemm` 做 16 次乘加。网格的 x 轴沿 C 的列。

### v2 · Tiled（`v2_tiled.py`）

算法与 v1 相同，下标换成 layout：`local_tile` 取 tile，tiled copy 做 gmem → smem，tiled MMA 划分每个线程的输出，边界用谓词张量。为了让不完整的 k-tile 只出现在开头，把 A、B 沿 k 向前移了一段，并先把 smem 清零。网格的 x 轴改成沿 C 的行。

### v3 · Pipelined（`v3_pipelined.py`）

照 CuTe 的 `ampere/sgemm.py` 示例：128 × 128 的 tile，每个线程 8 × 8 个输出，三段 `cp.async` 流水线，A 的 smem 步长加 4 以错开 bank。边界仍然用谓词在内核里处理。网格的 x 轴回到沿 C 的列。

### v4 · Aligned（`v4_aligned.py`）

把 v3 的边界处理全部拿掉。`solve` 判断尺寸：各维都是 tile 的整数倍、且至少有 3 个 k-tile 时走流水线内核，否则走一个线程算一个输出的 `_gemm_any`。

### v5 · Tensor core（`v5_tensor_core.py`）

保留 v4 的框架，把 FP32 乘加换成 FP16 的 tensor core MMA（16 × 8 × 16，FP32 累加）。每个输入拆成两个 FP16，`a = hi + lo / 2048`；乘积取 `hi·hi` 和两个校正项，丢掉相对大小 2⁻²² 的 `lo·lo`。主乘积每 16 步从零开始，结果在 MMA 之外用 FP32 累加。

### v6 · Warpgroup（`v6_warpgroup.py`）

H100 的版本：warpgroup MMA 只在 Hopper 上能编译。一条指令是 64 × 128 × 16，两个操作数都直接读 smem，所以 smem 里放的是 FP16 的两半。每个线程用 128-bit 读取把自己那份 FP32 从 gmem 读进寄存器，拆一次，写进 FP16 的 tile；A 沿 k 连续、B 沿 n 连续，与它们在 gmem 里一样。MMA 是异步的，线程在它运行时准备下一个 k-tile。`lo` 不再放大，校正项和主乘积进同一个 MMA 结果，每 32 步 k 并入一次 FP32 累加器。

### v7 · tcgen05（`v7_tcgen05.py`）

B200 的版本：tcgen05 MMA 只在 Blackwell 上能编译。数据的路径与 v6 相同。MMA 由一个线程为整个 128 × 128 的 tile 发出，结果累加在 tensor memory 里而不是寄存器里；线程每个 k-tile 等 MMA 结束，把结果读出来加进 FP32 累加器。线程不再持有 MMA 的结果，所以一个 CTA 用 512 个线程，一个 k-tile 加深到 64 步 k。
