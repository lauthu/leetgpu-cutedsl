# Vector Addition

[LeetGPU 题目](https://leetgpu.com/challenges/vector-addition) · challenge 1 · 官方定义 `1_vector_add` · 语言 `cute`

## 题目

`A`、`B`、`C` 是 GPU 上长度为 `N` 的连续一维 `float32` Tensor。计算 `C[i] = A[i] + B[i]`，结果直接写入 `C`。约束为 `1 ≤ N ≤ 100,000,000`。

- 性能测试：`N = 25,000,000`，`A`、`B` 在 [-1000, 1000) 上均匀分布
- 判定：`atol = 1e-05`，`rtol = 1e-05`

## 结果

Latency 是平台在性能测试上 15 次计时的中位数，包含 `solve` 调用的 Python 启动开销和一次设备同步，不包含编译。所有数字来自平台记录；本机没有 CUDA，未做本地验证。

## 分析

- **结论：** H100 上未能区分 v1 和 v2。v2 的两次提交（0.23426、0.25513 ms）都比 v1 的一次提交（0.27299 ms）快，但 v2 自身两次提交相差 8.9%，大于它与 v1 最保守的差距 6.5%，而且 v1 只有一次测量。
- **做到了多少：** 性能测试读 `A`、`B`，写 `C`，共 12 × 25,000,000 = 300 MB。按中位 latency，v1 为 300 MB ÷ 0.27299 ms ≈ 1.10 TB/s，v2 为 300 MB ÷ 0.24470 ms ≈ 1.23 TB/s。计时含 Python 启动和设备同步，所以这是 kernel 实际带宽的下限。
- **原因：** 推测。两版搬运的字节数相同，v2 只减少了每线程的访存指令数和 block 数。如果耗时主要由显存带宽和固定开销决定，这类改动的收益会很小，与目前"未能区分"一致，但没有测量证实。
- **下一步：**
  1. 在同一天把 v1 和 v2 各再提交 3 次（H100）。v2 最慢的一次仍比 v1 最快的一次快，且差距超过波动，才能说 v2 更快。
  2. 新增 v3，只把每线程元素数从 4 改为 8，与 v2 对比。仍在波动之内，说明每线程指令数不是瓶颈。

## 版本

### v1 · Scalar（`v1_scalar.py`）

每个线程处理一个元素：下标为 `bidx * block_size + tidx`，检查越界后执行 `C[i] = A[i] + B[i]`。block 为 256 线程，grid 为 `ceil(N / 256)`。这一版用来对应 CUDA 执行模型和 CuTe Tensor 索引，没有用到 CuTe 的 layout 和分块能力。

### v2 · Vectorized（`v2_vectorized.py`）

相对 v1，每个 block 处理 1024 个元素，256 个线程各取 4 个连续的 `float32`。用 `(线程, 元素)` layout 划分 tile，`autovec_copy` 在全局内存和寄存器 fragment 之间搬运。三个基地址都满足 16 字节对齐时，向编译器声明这一对齐；不足一个 tile 的尾部逐元素处理并检查越界。目的是减少访存指令数和 block 数；生成的指令没有检查过。
