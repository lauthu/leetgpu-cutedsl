# Matrix Addition

[LeetGPU 题目](https://leetgpu.com/challenges/matrix-addition) · challenge 8 · 官方定义 `8_matrix_addition` · 语言 `cute`

## 题目

`A`、`B`、`C` 是 GPU 上按行存放的 `N × N` 的 `float32` 矩阵。逐元素相加，`C[i][j] = A[i][j] + B[i][j]`，结果直接写入 `C`。约束为 `1 ≤ N ≤ 4096`。

- 性能测试：`N = 4096`，取值在 −1000 到 1000 之间
- 判定：`atol = 1e-05`，`rtol = 1e-05`

## 评审

标"自测"的数字不是提交记录。它们是 2026-11-23 在平台的 H100 上用附在 `make run` 里的脚本量的：`N = 4096`，在同一个进程里交替调用已经编译好的函数，4 轮、每轮 15 次，给出的是各轮中位数的范围；脚本不在仓库里。

### 结论

- **H100 现状：** 最好成绩是 v1 的 0.13778 ms，CuTe 的第 1 名；第 2 名 0.40135 ms 是它的 2.91 倍（0.40135 ÷ 0.13778）。最新的 v3 是 0.21318 ms，也低于第 2 名。
- **H100 版本之间：** 波动是实测的 13.1%，来自 v2 相隔 17 分钟的两次提交（0.18821 和 0.21289 ms）。按提交记录，v2 比 v1 慢 36.6%，超过波动；v2 和 v3 未能区分，相隔 40 秒的两次提交是 0.21289 和 0.21318 ms。
- **H100 v1 为什么快，没有定论：** 自测里 v1 和 v2 没有差别（0.0879–0.0897 和 0.0878–0.0923 ms），完整的一组元素在两版里由同样的线程访问同样的地址。四次提交按时间排是 0.13778、0.18821、0.21289、0.21318 ms，一路上升。两种解释现有数据分不开（推测）：平台在这 45 分钟里变慢了，或者 v2、v3 在平台的计时条件下确实比 v1 慢。v1 只有最早的一次提交。

### 代码

- `v3_minimal.py:51` **未验证**：`load()` 和 `store()` 在只保证 4 字节对齐的指针上生成什么指令，没有检查过。自测只确认了结果正确（缓冲区错开 4 字节，`N = 33` 和 `1000`）；v3 这个文件本身没有自测计时。
- `v2_per_thread.py:91-99` **多余**：对齐检查和两次 launch 没有可测的作用。自测里把三个缓冲区都错开 4 字节，走 4 字节对齐的分支（按 CuTe DSL 的源码，`autovec_copy` 这时退到 32-bit 访问），是 0.0873–0.0905 ms，与对齐时没有差别。v3 已经删掉。
- `v2_per_thread.py:56-66` **可读性**：三个寄存器 Tensor 和三次拷贝可以写成一行 `tC.store(tA.load() + tB.load())`，CuTe DSL 的官方示例 `elementwise_apply.py` 就是这样写的。自测里这种写法在 16 字节对齐的视图上是 0.0865–0.0907 ms。v3 已经换成这一行。
- `v3_minimal.py:45` **测试覆盖**：按线程选择路径后，11 个功能测试里有 10 个进入向量路径，v1 只有 32 × 32 一个。block 号大于 0 的情况，官方只有性能测试走到；v2 的自测补了 `N = 33`、`100`、`1000`、`4095` 和错开 4 字节的缓冲区，结果都正确，数据前后的保护元素没有被改写。
- `v1.py:1-6` **可读性**：docstring 还是 Vector Addition 的；内核的参数 `N`（第 30 行）是元素个数，而 `solve` 的 `N` 是边长；`A`、`A1`、`A16` 三个名字指同一块内存。v2 已经改掉。
- **做得好的：** 逐元素相加与行列无关，所以只在 `solve` 里把矩阵摊平，内核只看到一维（`v3_minimal.py:31-33`）。元素个数在 `solve` 里一次转成 `Int32`（第 65 行），内核里没有类型转换。

### 性能机会

**H100：** 单次结果低于 0.18523 ms 才算比 v3 快；最好成绩是 v1 的 0.13778 ms。空间：三个矩阵共 201.3 MB（3 × 16,777,216 × 4 字节）。自测里四种写法（v1、v2、load/store、4 字节对齐）都在 0.087–0.092 ms。扣掉 [Matrix Transpose](../3_matrix_transpose/README.md) 的自测量到的启动和同步 0.020 ms，是 201.3 MB ÷ 0.069 ms ≈ 2.9 TB/s，与那道题量到的读写速率相当。访问宽度从 128-bit 换成 32-bit 也不改变时间，所以内核受内存带宽限制，内核里没有余地（推断）。

没有值得花配额的机会。四次提交比自测（约 0.089 ms）多出 0.049–0.124 ms，这一部分的变化比内核里的改动能带来的都大，一次提交分不出来。建议把配额留给下一道题。

## 版本

### v1 · Flattened（`v1.py`）

`solve` 把三个 `N × N` 的矩阵各看成 `N²` 个元素的一维 Tensor，再交给 Vector Addition v2 的内核。一个 block 处理 1024 个元素，256 个线程各取 4 个连续的 `float32`，用 `autovec_copy` 在全局内存和寄存器 fragment 之间搬运；不足一个 tile 的尾部逐元素处理并检查越界。三个基地址都满足 16 字节对齐时，向编译器声明这一对齐。

### v2 · Per thread（`v2_per_thread.py`）

访问一整组元素的方式与 v1 相同，改的是结构，目的是整理代码，不是提速。`_flat` 一次建好一维视图和对齐声明，一块内存在 `solve` 里只有一个名字。每个线程拥有 4 个连续的元素：整组都在数据内就一起搬运，否则逐个处理并检查越界，不再有 1024 个元素的 tile。下标都是 `Int32`。

### v3 · Minimal（`v3_minimal.py`）

相对 v2 删掉两样东西，目的仍是整理代码。一是对齐处理：自测里 4 字节对齐的视图一样快，所以地址检查、第二次 launch 和第二个编译出来的 kernel 都不要了。二是寄存器 Tensor 和拷贝：一组元素直接在全局内存的 Tensor 上 `load()`、相加、`store()`。代码从 v2 的 48 行减到 29 行（不算注释和 docstring）。
