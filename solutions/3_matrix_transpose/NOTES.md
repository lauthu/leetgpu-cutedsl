# Matrix Transpose · 学习笔记

学习中的问答，针对 [v1.py](v1.py) 和 [v2_coalesced.py](v2_coalesced.py)。评测结果、评审和版本说明见 [README.md](README.md)。

下面用 M 表示 `rows`，N 表示 `cols`，例子都是 `A = [[1, 2, 3], [4, 5, 6]]`，也就是 M = 2、N = 3。

## Q&A

### 第一版写错了什么？

思路是对的：把一个 tile 读进 smem，再转置着写回去。错在四处，修改的地方在 `v1.py` 里用 `# FIX` 标出，原来的写法留在 `# was:` 后面。

- **`cute.make_tiled_copy_kv` 不存在**，CuTe DSL 4.4.2 里的函数是 `make_tiled_copy_tv`。本地的预检查不出这种错，要到平台上才报。
- **没有处理不完整的 tile。** 内核总是拷贝完整的 32 × 32，`rows`、`cols` 传进来却没有用。2 × 3 的示例会往 6 个元素的输出里写 1024 个元素。官方用例里只有 8192 × 8192 没有不完整的 tile。
- **输出视图的步长错了。** 原来是 `(N, M) : (1, N)`，这是把*输入*的 layout 换了两个 mode，不是输出的。
- **tile 内部没有交换坐标。** 第二次拷贝读 `s` 和写输出用的是同一个坐标。

在与 32 对齐的尺寸上用 Python 仿真下标映射：64 × 64 时 4096 个输出里 2048 个是错的（所有不在对角线上的 tile），改对 layout 之后是 0 个。

### A、B、Bt 是什么关系？

三个都是视图，不是三份数据。`A` 看的是输入，`B` 和 `Bt` 看的是同一块输出内存。

| | `A` | `B` | `Bt` |
| --- | --- | --- | --- |
| 内存 | 输入 | 输出 | 输出，与 `B` 相同 |
| 形状 | M × N | N × M | M × N |
| 存放 | 按行 | 按行 | 按列 |
| Layout | `(M, N) : (N, 1)` | `(N, M) : (M, 1)` | `(M, N) : (1, M)` |
| 元素 | `A[i, j] = input[i][j]` | `B[j, i] = output[j][i]` | `Bt[i, j] = output[j][i]` |
| 偏移 | `i·N + j` | `j·M + i` | `i + j·M` |

`B` 和 `Bt` 找到的是同一个位置，只是两个坐标的先后不同：`Bt[i, j]` 就是 `B[j, i]`。

题目要求 `output[j][i] = input[i][j]`，用这两个视图写出来就是 `Bt[i, j] = A[i, j]`。所以内核里没有任何"交换下标"的代码，交换在 `Bt` 的 layout 里（`v1.py` 第 104-106 行）。

### 换 mode 时哪些东西一起动？

一个 layout 是若干个 mode，每个 mode 有自己的大小和步长。转置一个视图就是把 mode 换个先后，大小和步长跟着 mode 一起走，不能只换其中一个。

| 视图 | mode 0：大小、步长 | mode 1：大小、步长 | Layout |
| --- | --- | --- | --- |
| `A` | M、N | N、1 | `(M, N) : (N, 1)` |
| `B` | N、M | M、1 | `(N, M) : (M, 1)` |
| `Bt`，把 `B` 的 mode 对调 | M、1 | N、M | `(M, N) : (1, M)` |

容易犯的错是只换步长、不换形状，写成 `(N, M) : (1, M)`。检查办法：`A[i, j] = Bt[i, j]` 要对所有的 (i, j) 成立，`Bt` 的形状就必须和 `A` 一样，是 (M, N)。

另一个容易混的式子是 `(N, M) : (1, N)`。它是"N × M 的矩阵按列存放"的 layout，但描述的是另一种字节排列：它其实是 `A` 的 mode 对调，也就是把输入内存读成 Aᵀ。第一版的错误正是把它用在了输出上。

### 用 `A = [[1, 2, 3], [4, 5, 6]]` 看一遍

输入内存，读作 `A`（偏移 `3·i + j`）：

| 偏移 | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| 值 | 1 | 2 | 3 | 4 | 5 | 6 |
| 名字 | `A[0,0]` | `A[0,1]` | `A[0,2]` | `A[1,0]` | `A[1,1]` | `A[1,2]` |

结果是 `B = Aᵀ = [[1, 4], [2, 5], [3, 6]]`，按行存放，所以输出内存最后应当是 `1, 4, 2, 5, 3, 6`。同一块内存有两套名字：`B[j, i]` 在偏移 `2·j + i`，`Bt[i, j]` 在偏移 `i + 2·j`。

| 偏移 | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| 值 | 1 | 4 | 2 | 5 | 3 | 6 |
| 读作 `B` | `B[0,0]` | `B[0,1]` | `B[1,0]` | `B[1,1]` | `B[2,0]` | `B[2,1]` |
| 读作 `Bt` | `Bt[0,0]` | `Bt[1,0]` | `Bt[0,1]` | `Bt[1,1]` | `Bt[0,2]` | `Bt[1,2]` |

- 读作 `B`：三行是 `[1, 4]`、`[2, 5]`、`[3, 6]`，是 Aᵀ。
- 读作 `Bt`：`Bt[0, ·]` 是偏移 0、2、4，即 `[1, 2, 3]`；`Bt[1, ·]` 是偏移 1、3、5，即 `[4, 5, 6]`。是 A。

跟一个元素走一遍：`A[0, 1] = 2` 在输入的偏移 1。内核把它写到 `Bt[0, 1]`，输出的偏移 `0 + 2·1 = 2`。偏移 2 的另一个名字是 `B[1, 0]`，而 `B[1, 0]` 正应该是 2。一般地，`A[i, j]` 拷到 `Bt[i, j]`，也就是 `B[j, i]`。

### 既然 B = Aᵀ，Bt = Bᵀ，为什么 Bt 不"等于"A？

作为矩阵它们相等，作为存放方式不相等。关键是之前一直没提的一件事：`A` 按行存放，`Bt` 按列存放。

一个矩阵按列存放时占用的内存，与它的转置按行存放时完全一样。

- A 按行存放：`1, 2, 3, 4, 5, 6`
- A 按列存放：`1, 4, 2, 5, 3, 6`
- Aᵀ 按行存放：`1, 4, 2, 5, 3, 6`

后两个是同样的字节。所以内核做的事其实不是"转置"，而是把 A 改成按列存放，写进输出内存；这块内存按行读就是 Aᵀ。

另外，"B = Aᵀ"是目标，不是已知条件：内核开始时输出内存里还什么都没有。`Bt = Bᵀ` 是视图的定义，所以"B = Aᵀ"和"Bt = A"是同一句话，内核让它成立的办法就是把 `A[i, j]` 拷给 `Bt[i, j]`。

### 转置和换 mode 有什么区别？

两者都得到"转置后的矩阵"，一个改的是描述，一个改的是字节。

| | 换 mode | 转置数据 |
| --- | --- | --- |
| 例子 | `B` → `Bt` | `A` → `B` |
| 内存 | 同一块 | 另一块 |
| 改变的是 | layout：两个 mode 对调 | 值在内存里的次序 |
| 存放方式 | 变了（按行变成按列） | 不变（都是按行） |
| 代价 | 没有，编译期完成 | 每个值都要搬一次 |

题目要的是第二种：检查程序把输出当作按行存放的 N × M 矩阵来读，不接受"还是那块输入，请按列读"。PyTorch 里有同样的区分：`A.t()` 返回一个共用内存、步长对调的视图，`A.t().contiguous()` 才真的搬数据。

内核用不花代价的那一种（`B` → `Bt`），把要花代价的那一种（`A` → `B`）变成一次坐标对坐标的拷贝。

### 那么内核做的只是把 A[i, j] 拷到 Bt[i, j] 吗？

是的。其余的代码决定的是怎样拷，不是算什么。

- **Tile：** `gA` 和 `gB` 从两个视图里切出同一个 32 × 32 的窗口，tile 内部是元素 (m, n) 拷到元素 (m, n)。
- **smem：** 值走 `gA → s → gB`，每一步的 (m, n) 都相同。这一段对正确性没有必要，是为了读可以沿 `A` 连续的方向、写可以沿 `Bt` 连续的方向，两个方向不一样。
- **`limit`：** 这个 tile 有多少行、多少列在矩阵里面。两个谓词由它算出，让拷贝跳过矩阵之外的 (m, n)。

一个线程处理一个元素、只做 `Bt[i, j] = A[i, j]` 再加越界判断的内核，同样是正确的。

### `copy_in` 的 layout 是怎么来的？是向量化读取吗？

```python
copy_in = cute.make_tiled_copy_tv(
    atom, cute.make_layout((8, 32), stride=(32, 1)), cute.make_layout((1, 1))
)
```

- `atom` 是一次 32-bit 的拷贝，一个 `float32`。
- `(8, 32) : (32, 1)` 是线程的 layout：把 256 个线程放在 8 行 × 32 列的小块上，位置 (m, n) 属于线程 `32·m + n`。
- `(1, 1)` 是值的 layout：每个线程在自己的位置上拷一个值。

推出这个 layout 的三步：`A` 沿 n 连续，所以线程号沿 n 递增，第二个 mode 的步长是 1；第二个 mode 取 32，一个 warp 正好是一行，32 个线程读相邻的 32 个 `float32`；256 / 32 = 8 行，跨一行跳过 32 个线程号，第一个 mode 的步长是 32。

```text
            n = 0 ........ 31
m = 0   线程   0 ..  31     warp 0
m = 1   线程  32 ..  63     warp 1
 ...
m = 7   线程 224 .. 255     warp 7
```

小块只有 8 行，tile 有 32 行，所以 `partition_S(gA)` 把它沿 m 重复 4 次：一共 4 轮，每轮每个线程拷一个元素，每个 warp 拷一行。线程 37 在 m = 1、n = 5，拷的是 tile 里的 (1, 5)、(9, 5)、(17, 5)、(25, 5)。

它是合并访存，不是向量化读取，这是两回事：

- **合并（coalesced）** 说的是一个 warp 的各个线程：一条指令的 32 次标量读取落在连续的 128 字节上。`copy_in` 是这样。
- **向量化** 说的是一个线程内部：一条指令读 4 个 `float32`。`copy_in` 不是，因为 atom 是 32 bit，值的 layout 是 `(1, 1)`。

### `copy_out` 的线程怎么分配？为什么 layout 不一样？

仍然是每个线程每轮一个值、一共 4 轮，变的是小块的形状：`copy_in` 的小块是扁的（8 行 × 32 列），`copy_out` 的是高的（32 行 × 8 列）。每次拷贝都让 warp 顺着它碰到的那块全局内存的连续方向排：`copy_in` 读 `A`，沿 n 连续；`copy_out` 写 `Bt`，沿 m 连续。中间隔着 smem，两次拷贝才能用不同的分配方式。

v1 和 v2 的小块相同，线程号的编法不同：

| | v1（`v1.py` 第 62-64 行） | v2（`v2_coalesced.py` 第 75-79 行） |
| --- | --- | --- |
| Layout | `(32, 8) : (8, 1)` | `(32, 8) : (1, 32)` |
| 位置 (m, n) 的线程 | `8·m + n` | `m + 32·n` |
| 线程号沿 | n 递增 | m 递增 |
| 一个 warp 覆盖 | 4 行 × 8 列 | 一列的 32 行 |
| 一个 warp 的一次写 | 8 处，每处 4 个值 | 相邻的 32 个值 |

v2 里线程 37 在 m = 5、n = 1，写的是 (5, 1)、(5, 9)、(5, 17)、(5, 25)。而它在 `copy_in` 里读的是 (1, 5)、(9, 5)、(17, 5)、(25, 5)：一个线程写的不是它自己读的，所以两次拷贝之间要有 `sync_threads()`。

v2 里一个 warp 读的是 `s` 的一列，地址是 `33·m + n`，落在 32 个不同的 bank 上，这就是行步长取 `BN + 1` 的用处。

### CuTe 怎样理解线程的 layout？是把 tid 当坐标代进去吗？

方向反过来。你写的 layout 是从位置到线程号的函数：(m, n) → `32·m + n`。CuTe 把它和值的 layout 合起来再求逆，得到 TV layout：(线程号, 值的序号) → 小块里的位置。对 `copy_in` 来说就是 `tid → (tid div 32, tid mod 32)`。同时记下小块的大小 (8, 32)。

用的时候分两步：

1. `copy_in.get_slice(tid)` 把 TV layout 的线程坐标固定成本线程的编号。
2. `thr_in.partition_S(gA)` 把张量按小块的大小切开，每个小块通过 TV layout 改用 (线程, 值) 来索引，只留下本线程的那一份。

得到的是一个"我的元素"小张量，形状是（每个位置的值数、沿 m 的重复、沿 n 的重复），对 32 × 32 的 tile 是 (1, 4, 1)。这些都是编译期的 layout 运算，运行时只剩几次整数运算把 `tid` 变成地址。

可以这样记：你描述的是"哪个线程坐在哪里"，CuTe 从中推出"线程 `tid` 坐在哪里"。

### "已经接近内存带宽"是怎么量出来的？

没有直接量带宽，是从计时里推出来的：在一次自测里把内核的两半轮流去掉。下面是平台 H100 上 7000 × 6000 的进程内计时（15 次调用的中位数），不是提交记录。

| 运行的内容 | 中位数 |
| --- | ---: |
| 完整的内核（v2 的做法） | 0.1387 ms |
| 去掉输出拷贝，只做 gmem → smem | 0.0751 ms |
| 去掉输入拷贝，只做 smem → gmem | 0.0802 ms |
| 32 × 32 的问题，只有一个 tile：只剩启动和同步 | 0.0201 ms |

转置的一边要搬 7000 × 6000 × 4 字节 = 168 MB。

- 读：0.0751 − 0.0201 = 0.055 ms，约 3.05 TB/s。
- 写：0.0802 − 0.0201 = 0.060 ms，约 2.8 TB/s。
- 验算：0.0201 + 0.055 + 0.060 = 0.135 ms，完整内核量到的是 0.1387 ms，相差不到 0.004 ms，所以把它们当作可以相加的几部分是合理的。

拿来比较的"H100 的内存带宽约 3.35 TB/s"是凭记忆的数字（NVIDIA 的 H200 资料给的是 4.8 TB/s，并说是 H100 的 1.4 倍），没有在这次工作里核对。

这个方法的限度：两半各只量了一次；只写的那个变体写出去的是 smem 里的随便什么值，只有时间有意义；输入比 cache 大得多，读应当来自内存而不是 cache，但没有单独验证。

量 v1 和 v2 的差别时还发现，一个进程里第一次量大尺寸总是偏慢，所以最后是先预热，再交替量 4 轮：v1 是 0.169–0.171 ms，v2 是 0.138–0.139 ms。

### 还能再优化吗？向量化读取，或者把边界 tile 移出内核？

两个想法都合理，但已有的测量说它们都动不了多少。

- **向量化读取** 减少的是指令数，不是字节数。一个 warp 的标量读取已经合并成一次 128 字节的访问。读这一边约 3.05 TB/s，即使到 3.35 TB/s 也只省 0.005 ms 左右。更大的 tile（更少、更长的访问）没有带来变化，也说明代价跟着字节数走。它还需要运行时检查 `cols` 是 4 的倍数、地址按 16 字节对齐，并且要改 smem 的填充。
- **把边界 tile 移出内核**：较弱的形式已经量过，完整的 tile 在内核里用一个分支跳过谓词，时间还是 0.138–0.139 ms。矩阵乘法里谓词贵，是因为它们在一个 384 次的循环里；这里每个 CTA 只做 8 次带谓词的拷贝，不完整的 tile 也只占 1% 左右。移到第二个内核还要多一次启动，而一次启动加同步量到的是 0.020 ms。

时间的去向：

| 部分 | 时间 | 来源 |
| --- | ---: | --- |
| 启动和同步 | 0.020 ms | 自测 |
| 读 168 MB | 0.055 ms | 自测 |
| 写 168 MB | 0.060 ms | 自测 |
| 内核之外 | 约 0.10 ms | v1 的提交 0.26903 ms 减去它的自测 0.171 ms |

最大的一项是最后一行，而它是什么还不知道。平台每次计时都用新生成的输入，并先清 cache；自测重复用同一对缓冲区。如果要继续，下一步是在自测里每次调用都新建输入和输出，看这 0.1 ms 会不会出现。这个实验没有做。
